# zygiella

## 0.1.1

### Patch Changes

- 2b3d815: Lower the memory a watcher needs to read a large directory, which is most of what its first scan costs. Reading a directory used to start one task for every entry of it at once, so watching a tree of 20,000 files grew the resident set by 145 to 164 MB on macOS and about 200 MB on Linux, and Node with `--max-old-space-size=64` ran out of memory while scanning. Reading a directory now hands its entries to workers that share a budget of 256 on each level of nesting, as readdirp (the directory walker of chokidar) does with its batches of 256, and the same tree grows it by 17 to 39 MB. The events reported do not change, and on CI the time until `ready` was shorter or within the noise of the runners in every tree shape measured.
- 3b6dab1: Do not report what is already there when a native event arrives while the first scan is still reading. With `ignoreInitial: true`, a directory of 1100 files that was created just before `watch()` could be reported as 1100 `add` events: macOS can deliver the events of files created just before watching after the watcher has started, the directory read that such an event starts ran at the same time as the first scan, and it saw the entries that the scan had not recorded yet as new. A read that an event starts now waits for a scan of the root above it that is making the baseline (the first scan, not a `rescan()`), as chokidar serializes its work per root.
- 50f662a: Report a file that is created right after a watched path that did not exist yet appears. `watch("/work/later")` with `/work/later` created and `/work/later/a.txt` written at once reported `addDir` but sometimes never `add` (about 5 in 1000 on a loaded macOS machine), because the native watch of the new directory is attached before the first read of it, but the OS only starts delivering a little later, so a file made in between is neither in that listing nor announced. The directory, and the directories below it that were read, are now read once more 50 ms after the first read, as `ready` already waits 50 ms.
- e2adbd9: Report `add` and `change` as soon as the file is known to have content, instead of 50 ms after its last event. Creating 500 files in one directory used to report the first `add` after 0.5 to 1.2 s on a tree of 20,000 files, because a re-read of the directory that saw a file still being written started its 50 ms wait again.

  - The first report of an `add` or `change` of a file that is not empty is made at once. A file that is still empty is held for 10 ms for its data (Linux reports a truncate before the write), and is reported at once if a native event for it arrives in that time.
  - A write that arrives as several events is now reported as two events: `add` (or `change`) at once with the content so far, then `change` at the end of the burst. A file that is written in two steps 30 ms apart, `"x"` and then 1000 more bytes, used to be reported as one `add` that already had 1001 bytes; it is now an `add` at 1 byte and a `change` at 1001 bytes. A listener that reads the file on `add` and needs all of it should use `awaitWriteFinish`.
  - The first `add` of a file waits for the directory reads that are going on at that moment, but for 50 ms at most, so that a file moved within a directory (`a.txt` to `b.txt`) still reports `add` of `b.txt` with `renamedFrom: "a.txt"`. A move to another directory keeps `renamedFrom` only if the removal is read while the `add` is still waiting, which holds when the read of the old directory has started by the time the `add` is announced; if that read starts later, the `add` carries no `renamedFrom` (the `unlink` is still reported). In a directory of more than 1000 entries, whose entries are read one by one, the `add` does not wait: if the removal is read after the `add` was reported, the `add` carries no `renamedFrom`, which the 50 ms wait used to leave room for.
  - `awaitWriteFinish` and `atomic` are unchanged.

## 0.1.0

### Minor Changes

- ecdb57f: Add the `followSymlinks` and `atomic` options, both on by default as in chokidar.

  - A symbolic link to a directory used to be reported as `addDir` and never descended into. It is now descended into, and files below it are reported under the link's path (a link to a directory already on the way down, such as a link back to an ancestor, is still not descended into). Pass `followSymlinks: false` to watch a link as itself: it is reported as `add`, and pointing it somewhere else is reported as `change`.
  - The `unlink` of a file that is deleted by itself is now reported 100 ms late (the files below a removed directory and `unlinkDir` are still reported at once). A file deleted and created again within that time (how vim saves) is reported as one `change` instead of `unlink` then `add`. Pass `atomic: false` for the old timing, or a number for another window in ms. While `atomic` is on, editor temporary files (`.swp`, `.swx`, a trailing `~`, Sublime's `.subl*.tmp`) are ignored.

- 94226d4: Add `getWatched()`, the chokidar method that tells which directories are watched and what is in them. `watch("/work/src").getWatched()` returns `{ "/work": ["src"], "/work/src": ["a.ts", "sub"], "/work/src/sub": ["c.ts"] }`: absolute directory paths as keys, the sorted names of the files and directories watched directly in each as values. Skipped by `ignored` or below `depth`, they are not listed, and a directory at the `depth` limit is a name without a key of its own. It is `{}` after `close()`.
- 54591ce: Breaking: a `RegExp` in `ignored` is now tested against the path with `/` as the separator on every platform, as in chokidar v6. On Windows `C:\work\.git\config` is tested as `C:/work/.git/config`, so `/(^|\/)\../` matches, and a `RegExp` written for `\\` only (`/src\\gen/`) no longer does; `[\\/]` still works. Functions and strings are unchanged.

  A function in `ignored` that declares two parameters (its `length` is 2 or more) is now called once per path with `(path, stats)`, where `stats` is the `fs.Stats` of the path, so `ignored: (path, stats) => stats?.isFile() === true && !path.endsWith(".js")` descends into directories and skips other files. Unlike chokidar, which calls it with the path alone first, it is never called without `stats`. A function with one parameter is called with the path alone, and no `stat` is made for it.

  Add `watcher.rescan()`, which reads every watched path and directory again and reports the difference, for file systems where `fs.watch` is silent (Docker bind mounts, WSL2 `/mnt/c`, NFS, SMB).

- bdd6299: Watch a tree with one `fs.watch({ recursive: true })` on macOS (not with `depth`), and watch each directory behind a followed link on its own. Per-directory watches stop working on macOS above 4096 directories: every one of them fails with `EMFILE` and `ready` never arrives, and `close()` takes 20 s for 2000 directories. With a recursive watch `watcher.unwatched` lists the watched path instead of directories. Linux and Windows are unchanged.
- 11059ab: Add the `persistent` option. With `persistent: false` the watcher no longer keeps the process alive: the `fs.watch` handles and the internal timers (the quiet period, `awaitWriteFinish` polling, the `atomic` hold) are unref'd, so `watch(dir, { persistent: false })` left unclosed lets a script exit by itself. The default stays `true`, as before.
- b7439c7: `ready` now resolves to `{ missing: string[] }`, the paths given to `watch()` or `add()` that did not exist, and the `ready` event receives the same object. Missing paths are still watched once they appear.
- b7439c7: Emit `error` for directories and entries that cannot be read or inspected (`EACCES`, `EPERM`), including symbolic links whose target cannot be reached, instead of skipping them silently, and add `ignorePermissionErrors` to restore the old behavior. A watcher without an `error` listener now throws for such a path, so pass `ignorePermissionErrors: true` to keep skipping them.
- b05d400: Add `watcher.unwatched`, the directories that are read but have no native watch because `fs.watch` threw (`ENOSPC`, `EMFILE`) or the native watcher reported an error and could not be set up again. Until now the `error` event was the only sign, `ready` still resolved, and changes below such a directory were missed, with nothing to say afterwards which directories were left unwatched. `rescan()` now also tries to watch those directories again, so a caller that rescans on a timer recovers once the limit is raised or released. zygiella still does not rescan by itself.
- 46a3dca: Add the `rescanInterval` option. With `rescanInterval: 2000`, the watcher calls `rescan()` 2000 ms after `ready` and again 2000 ms after each read has finished, until `close()`, for file systems where `fs.watch` reports nothing (NFS, Docker bind mounts, `/mnt/c` in WSL2). With `persistent: false` the timer is unref'd, which a `setInterval` of your own is not. The default is 0 (no timer).
- 3f4c9d3: Report changes made while the process was not running. `watcher.snapshot()` returns the state of everything watched as a JSON-serializable `{ version, entries }` object, and the new `since` option takes it on the next start: the initial scan then reports only what was added, changed (size, mtime, inode or symbolic link target, as for a live `change`) or removed in between, as `add`, `change`, `unlink`, `addDir` and `unlinkDir` before `ready`. Saving and loading the snapshot is up to the caller. `since: null`, or a snapshot of another version, reports everything as `add`. `since` overrides `ignoreInitial`.

  A watched path that cannot be inspected for lack of permission is no longer reported as removed: what is below it stays as it was until it can be read again.

- df59924: `FSWatcher` is no longer a class: it is exported as a TypeScript type only, and `watch(paths, options)` returns a plain `EventEmitter` with the same methods, properties and events as before (`on`, `add`, `unwatch`, `rescan`, `close`, `snapshot`, `ready`, `unwatched`). Code that calls `new FSWatcher(paths, options)` must call `watch(paths, options)` instead, and `watcher instanceof FSWatcher` must be replaced, for example by `watcher instanceof EventEmitter`, which also accepts any other emitter. Importing `FSWatcher` as a value, as in `import { watch, FSWatcher } from "zygiella"`, now fails with a SyntaxError when the module loads, so use `import type { FSWatcher }` or `import { watch, type FSWatcher }` when you only need the type. Code that only receives a watcher from `watch()` and calls its methods is not affected. Internally the source is split into modules for path matching, option defaults, snapshots, native watch handles and waiting reports; the behaviour of `watch()` is unchanged.

### Patch Changes

- 4d3692e: Report a directory that was replaced by another directory under the same name. After `mv src src.old` and `mv staging src`, the files that were in `src` were never reported as removed and the files that are in it now were never reported as added, until another event of `src` or `rescan()`. A directory whose inode number differs from the one seen before is now reported as `unlinkDir` (with `unlink` for what was in it) and then `addDir` (with `add` for what is in it). A file system that reports inode 0 is not affected.
- bdd6299: In a directory with more than 1000 entries, inspect only the entry that `fs.watch` names instead of reading the whole directory on every event. A change in a directory of 30,000 files took 0.2 to 1 s to be reported because every event re-read it; the directory is read whole once, 1 s after its last event, so an entry whose event was lost is reported then if other events of that directory arrived; one lost with nothing after it stays missed until the next event or `rescan()`.
- cff5d2d: Report where a moved file came from: the `add` of a file that was moved carries `{ renamedFrom }` as its second argument (the third of `all`), found as a file that disappeared and one that appeared within 1 s with the same device, inode, size and mtime (best effort: not on a file system that reports inode 0, across file systems, or when either half is noticed late). `unlink` and `add` are reported as before.
- d166804: Do not report a second `change` for one write, a false `unlink`, or a file put back in the place of a directory, when a read of the file finishes late. A read that was in flight while the file was recorded as reported, or forgotten, is made again, whether it succeeded or failed and, with `followSymlinks: false`, including the read of the link target, so its older result no longer replaces the recorded size, mtime and target. A file that was missing at its read in a directory scan is looked at once more before it is reported as removed, as it may be back by the time the other names of the directory have been read.
- 242c050: Report one `add` or `change` for one write even when the native event for the finished write arrives after the quiet period. The file is read again when the quiet period ends and its size and mtime are recorded as reported, so a late event for a write that was already included no longer reports a second `change` (and a new file whose write finished late is reported as `add` only, not as `add` followed by `change`).
- bdd6299: Do not watch a directory again after its native watcher reported `EMFILE` or `ENOSPC`, and stop at the fourth error in a row without an event (the first three are retried). On macOS every handle gets `EMFILE` at once when the process holds too many watches, and watching them all again kept the process busy for good: `ready` never came. `rescan()` still tries again.
